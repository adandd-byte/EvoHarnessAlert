# order-service / payment-service 交易支付 Runbook

## 适用告警

- 下单失败率、支付成功率下跌（BUSINESS，P0/P1 高发）
- 支付回调延迟、MQ 积压、订单状态卡在"待支付"
- order 分库连接池耗尽、慢 SQL

## 业务上下文

order-service 创建订单并推进状态机（创建→待支付→已支付→已发券）；payment-service 负责收单与第三方渠道回调。用户感知是"付了钱没券/订单没状态"，资损敏感度最高。两个服务通过 MQ 解耦，回调链路是排障重点。

## 排查步骤

1. **定口径**：先确认支付成功率下跌是"渠道失败"还是"我方失败"：查渠道返回码分布。
2. **查回调链路**：payment 回调 → MQ → order 状态推进 → coupon 发券，逐跳确认积压点；MQ consumer lag 是关键指标。
3. **查订单状态机**：卡在"待支付"的订单量、超时关单任务是否正常。
4. **查数据库**：order 分库热点（热门店铺订单集中）、长事务、连接池水位。
5. **对账**：出现"支付成功但订单未更新"时立即触发支付对账，统计差异订单数。

## 止血动作

- 渠道故障：切换备用支付渠道（需支付负责人审批）。
- MQ 积压：扩容 consumer、临时提高消费并发；先保证回调幂等再提速。
- 连接池耗尽：限流非核心查询、kill 长事务。
- 疑似重复扣款：冻结差异订单自动推进，转人工对账。

## 升级条件

- 支付成功率跌破 90% 或持续时间超过 5 分钟 → P0，立即拉应急并通知支付渠道负责人。
- 对账发现真实资损 → 冻结相关订单并升级财务值班。

## 常见根因 Top

1. 第三方渠道抖动或证书过期
2. 回调验签失败/重试风暴
3. MQ 积压导致发券延迟
4. 热点店铺订单分库不均
5. 超时关单任务异常引发的状态卡单

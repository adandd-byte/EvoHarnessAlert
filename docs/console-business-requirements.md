# 告警控制台业务与展示需求

状态：需求基线与待实现示例，不代表现有功能已经完成。

本轮只整理需求，不修改前端、告警规则或现有数据集。依据用户确认的业务解释原则，以及飞书《告警助手代码级文档》第 2.4、12.4、18、19 节。

## 1. 产品目标

读者包括刚接触运维的开发者和实际值班人员。详情页必须先说明发生了什么、影响什么、证据是否可靠、下一步做什么，再提供技术字段。

中文名称优先，英文标识保留用于定位。不能通过翻译掩盖事实缺失，不能用模拟证据冒充生产取证。

## 2. 示例业务系统

设定为虚构的到店餐饮团购平台。以下职责、标识和团队均为项目演示约定，不对应外部公司的内部系统。

| 中文服务 | 技术标识 | 职责 | 示例负责团队 |
| --- | --- | --- | --- |
| 团购订单服务 | groupbuy-order-service | 创建订单、维护状态、协调交易流程 | 团购交易组 |
| 团购库存服务 | groupbuy-inventory-service | 预占、扣减与释放库存 | 商品库存组 |
| 支付服务 | payment-service | 发起支付、接收支付结果、通知订单服务 | 支付平台组 |
| 券码服务 | groupbuy-coupon-service | 发放团购券、维护券状态 | 团购权益组 |
| 到店核销服务 | groupbuy-redemption-service | 校验使用资格并协调核销记录 | 到店履约组 |
| 退款服务 | groupbuy-refund-service | 校验退款条件、协调资金与权益状态 | 团购售后组 |

业务步骤：创建待支付订单并预占库存 → 用户发起支付 → 接收支付结果 → 更新订单与库存状态 → 发放团购券 → 到店核销。

上述箭头表示业务先后关系，不承诺所有调用同步串行。支付结果通知及发券可以异步发生，故“付款成功但没有券”不能直接归因为支付服务故障。具体同步接口、异步消息、超时和幂等规则需在接口契约中补齐。

退款是独立分支：申请退款 → 检查订单与券状态 → 经授权调用退款能力 → 对齐资金、订单与券状态。告警助手无直接扣款、退款、改单或补券权限。

每个服务需维护：中文名、技术标识、业务职责、所属团队、上游、下游、接口、适用环境、监控口径、处理手册、版本和维护人。真实模式不得用示例团队填充未知负责人。

团购交易组查看支付平台异常时，要区分“本组可排查范围”和“需支付平台协查范围”。演示服务目录不构成真实跨团队授权。

## 3. 分开显示四种状态

| 维度 | 取值示例 | 不得混淆的概念 |
| --- | --- | --- |
| 数据来源 | 演练样本、后端接入 | 后端接入也可能是合成联调数据，不等于生产事故 |
| 业务运行环境 | 生产、预发布、开发、未提供 | 与页面是否连接后端无关 |
| 分析来源 | 案例预设判断、本次模型分析、规则兜底 | 后端连接成功不等于模型调用成功 |
| 动作状态 | 待排查、待审批、执行中、待验证、已恢复 | 提出建议不等于已执行，技术恢复不等于业务恢复 |

环境解释：生产（production）为实际提供业务服务的环境；预发布（staging）为上线前验证环境；开发（development/dev）用于开发调试。环境名本身不能证明是否含真实用户或数据，应服从实际环境配置。

演练允许模拟生产环境，但必须同时展示“演练样本”和“模拟生产环境”。现有 staging 样本不能只改中文后冒充 production 样本；环境或口径调整需要更新样本版本与预期结果。

## 4. 支付案例完整示例

### 4.1 案例身份与背景

- 名称：支付接口错误率告警，监控与日志结果不一致。
- 数据性质：新设计的合成演练案例，不是真实事故，也不是已执行的工具轨迹。
- 模拟业务环境：生产环境；演练本身在本地运行。
- 服务：支付服务（payment-service），负责发起支付和处理结果通知。
- 示例接口：POST /payments，本项目虚构接口，非已实现 API。
- 时间：2026-01-15 09:30–10:05，统一使用北京时间。
- 优先级：输入告警标记 P0，表示最高响应优先级；先响应，实际业务影响待核实，不因模型猜测自动升级或降级。
- 初始状态：尚未接手，尚未确认根因。

### 4.2 给用户的第一段说明

“支付服务收到最高优先级告警。监控样本报告某异常实例组的支付接口错误率达到 100%，但日志样本中的另一组实例错误率约为 0.2%。目前尚未确认两份数据覆盖相同请求范围，因此不能认定整个支付服务全部失败。请先核对接口、实例、时间与采样范围。”

这里是待核对的不一致观测，不是已经证明的逻辑矛盾。若最终确认分别覆盖不同实例，两者可能同时成立。

### 4.3 可能的业务影响

可能影响用户发起支付。支付失败人数、涉及订单数、地域和持续时长尚无可靠数据，不能编造。另需核实是否存在支付已成功但订单未更新的情况，避免把技术错误率直接等同于交易失败率。

### 4.4 证据清单

| 用户看到的名称 | 演练中提供的内容 | 当前能说明什么 | 尚不能说明什么 |
| --- | --- | --- | --- |
| 证据 1：支付错误率监控 | 指定异常实例组报告 100% 服务端错误 | 该监控口径下出现异常观测 | 整个支付服务全部失败、资金受损 |
| 证据 2：支付访问日志 | 另一实例组约 0.2% 错误率 | 日志观测与前者不同，需核对范围 | 可以否定前者或确认监控误报 |
| 待补充：失败请求调用链 | 尚未提供 | 当前没有该项证据 | 已定位到某下游服务 |
| 待补充：最近发布记录 | 尚未提供 | 无法核对发布相关性 | 最近发布就是根因 |
| 待补充：异常栈与代码 | 尚未提供 | 无法定位具体函数或代码行 | 代码修改已被证明能修复 |

成功返回工具请求只代表取得结果，不自动意味着证据充分。空白、占位说明、无内容快照不得标为“已完成取证”。

每份证据展开后应展示：内容、来源、查询条件、时间范围、环境、服务/实例范围、采样与统计口径、采集状态、可访问的原始引用。内部 Evidence ID 保留在详情或复制功能中，不作为主要名称。

### 4.5 下一步排查

1. 核对监控和日志是否来自同一环境、接口、时间窗口、版本及实例组。
2. 核对错误率分母、错误码分类、采样比例和采集延迟。
3. 选取失败请求，补充调用链与对应日志；若没有权限，发起明确的跨团队协查。
4. 对照异常与正常实例的版本、依赖和资源状态。
5. 取得最近发布记录后再判断是否存在发布相关性，不把“先后发生”当因果证据。

页面需显示每一步是预设步骤、实际待执行任务、真实执行中，还是已有结果，不能把整个预设流程都画成已完成。

### 4.6 处理建议与安全条件

当前建议：继续补充证据并联系支付平台值班人员，提交冻结非必要自动变更的建议。此建议本身不表示已经冻结。

回滚仅是条件分支：如果证据支持特定发布与异常相关，且确认目标服务、版本、兼容性、权限及风险，才提交人工审批。页面不能孤立展示“回滚支付服务”作为默认答案。

故障处理手册（Runbook）不是一条操作命令。至少包含适用范围、预检查、排查步骤、允许的动作、审批条件、失败回退和恢复验证。手册建议是经验依据，不是本次故障证据。

恢复验证：在相同统计口径下检查接口错误率、支付成功率、订单状态推进、券发放延迟及遗留补偿问题。阈值和观察时长需由服务约定提供，未知时明确标注待填写。

## 5. 页面信息顺序

1. 事件摘要：中文服务、业务影响、优先级、来源与环境、当前状态。
2. 当前判断：已知事实、待验证假设、无法判断的内容，附分析来源。
3. 排查进展：做过什么、结果怎样、哪里阻塞、下一步是什么。
4. 证据：按可读名称展示，点击查看原始内容与范围。
5. 处理建议：适用前提、风险、权限、审批、执行结果和恢复验证。
6. 技术详情：内部编号、原始负载、模型记录和完整协作轨迹。

常用操作和事实信息优先可见。术语解释随字段提供简短说明或可访问的展开解释，不用大段帮助文案占满工作区。

## 7. 实现前的验收标准

- 新读者能从详情说明服务职责、可能影响和下一步排查，不必先看 JSON。
- 演练预设、真实模型输出、规则兜底及实际执行记录不会混淆。
- 所有判断能定位到证据；不一致结果展示双方范围，缺证据就明确缺失。
- 无真实指标、日志、代码或时间时不伪造；演练中补写的内容明确为合成并有版本。
- 无条件、无依据的回滚建议不得作为默认处理结论。
- 演练操作不投递后台、不调用模型；需要真实投递时有独立入口和明确目标。
- 先完成这条支付样本的数据合同和展示验收，再批量迁移其余场景，保留旧样本版本供回归对照。

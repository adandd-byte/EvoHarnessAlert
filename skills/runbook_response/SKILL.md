# 技能：处置建议（runbook_response）

根据已确认证据生成面向值班人员的中文处置报告。原则：**先止血、后定位、再长期修复**。

## 1. 输入

| 输入 | 说明 | 优先级 |
| --- | --- | --- |
| 告警事实 | 标题、描述、等级、类型、状态、时间窗口 | 必须 |
| 日志证据 | 错误日志、异常堆栈、关键 trace | 强证据 |
| 指标证据 | 错误率、延迟、饱和度、依赖指标 | 强证据 |
| 代码证据 | 相关接口、模块、近期变更 | 支撑 |
| 知识库片段 | Runbook、历史故障、SOP | 支撑 |

> 证据分级：`strong`（原文/日志/大盘）、`medium`（标签/注解）、`weak`（推断）。缺失证据必须显式标注。

## 2. 处置流程

1. **归纳事实**：从输入中提炼已确认事实、未确认推测、待验证项。
2. **先止血**：给出立即可执行、可回滚的止血动作（摘流量、重启单实例、止损开关、降级等）。高风险动作标注“需人工审批”。
3. **再定位**：按 日志 → 代码 → 大盘 → 知识库 逐层给出定位步骤。
4. **长期修复**：给出根因修复、监控补强、发布门禁等长期建议。
5. **P0/P1 通知文案**：包含影响范围、负责人、当前动作、下一次同步时间。
6. **输出报告**：按第 3 节结构输出中文报告。

## 3. 输出结构（JSON）

```json
{
  "severity": "P1",
  "alertType": "PROBLEM",
  "summary": "处置结论一句话",
  "immediateActions": [
    {"action": "止血动作", "requiresApproval": false, "rollback": "回滚方案"}
  ],
  "locateSteps": [
    {"step": "定位步骤1", "evidence": ["source", "strength"]},
    {"step": "定位步骤2", "evidence": []}
  ],
  "longTermFixes": ["长期修复建议1", "长期修复建议2"],
  "notification": {
    "recipient": "值班/负责人",
    "impact": "影响范围",
    "currentAction": "正在执行的动作",
    "nextSyncAt": "下一次同步时间"
  },
  "missingEvidence": ["缺失的证据1", "缺失的证据2"]
}
```

## 4. 编写规范

- 短句、步骤化表达，先止血再定位。
- 每条关键结论附证据来源或明确说明缺失证据；不臆造不存在的 Runbook。
- 涉及密码、Token、密钥、连接串时必须脱敏并提示，不复述完整敏感值。
- P0/P1 必须给出负责人、同步机制与人工确认点。

## 5. 安全边界

不得泄露敏感字段，不得臆造不存在的 Runbook，不得建议未经审批的生产变更。所有自动修复动作必须标注人工确认点和回滚方案。
